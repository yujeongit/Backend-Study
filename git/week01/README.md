### 1장. 깃 시작하기 (p.11~36)

### 1. 깃이 하는 일 3가지
- **버전 관리**: 문서를 수정할 때마다 언제, 무엇을 바꿨는지 기록해 두는 것
- **백업**: 지역 컴퓨터가 아닌 다른 곳(대표적으로 깃허브 같은 원격 저장소)에 복제해 두는 것
- **협업**: 여러 사람이 원격 저장소를 통해 파일을 주고받으며 함께 작업하는 것

### 2. 설치 시 기억해 둘 포인트
- 기본 편집기로 **VS Code**를 선택하면 깃 배시(Git Bash)를 따로 켜지 않고 VS Code 내장 터미널에서 깃 명령을 쓸 수 있음. 
- 최신 깃부터는 기본 브랜치 이름이 `master`가 아니라 **`main`** 임. (예전 버전으로 설치한 저장소는 여전히 `master`를 쓸 수도 있음)

### 3. 알아 둬야 할 리눅스 명령어
| 명령 | 기능 |
|---|---|
| `pwd` | 현재 경로 출력 |
| `ls`, `ls -l`, `ls -a`, `ls -r`, `ls -t` | 파일 목록 (상세정보/숨김파일/역순/시간순) |
| `cd 디렉터리명` / `cd ..` / `cd ~` | 디렉터리 이동 / 상위로 / 홈으로 |
| `mkdir 이름` | 디렉터리 생성 |
| `rm -r 이름` | 디렉터리(하위 포함) 삭제 |
| `clear` | 터미널 화면 지우기 |
| `exit` | 터미널 종료 |

디렉터리 기호: `~`(홈), `.`(현재), `..`(상위 디렉터리)

### 4. 깃 사용자 정보 등록 (최초 1회)
```bash
git config --global user.name "이름"
git config --global user.email "이메일"
```

### 2장. 깃으로 버전 관리하기 (p.37~78)

### 1. 깃의 3단계 작업 영역
1. **작업 트리(working tree)**: 실제로 파일을 만들고 수정하는 공간
2. **스테이지(stage / staging area)**: 버전으로 만들 파일이 대기하는 공간
3. **저장소(repository)**: 스테이지의 파일이 실제 버전(커밋)으로 저장되는 공간

깃 작업 흐름은 **작업 트리에서 수정 → `add`로 스테이지에 올림 → `commit`으로 저장소에 버전 생성**

### 2. 기본 명령
```bash
git init                       # 현재 폴더를 저장소로 초기화
git status                     # 현재 상태 확인
git add 파일명                  # 스테이지에 올리기 (add . 은 전체)
git commit -m "메시지"          # 커밋(버전) 생성
git commit -am "메시지"         # 한 번이라도 커밋된 파일의 add+commit 동시 처리
git log                        # 커밋 기록 확인
git log --stat                 # 커밋별 변경 파일 통계까지 표시
git diff                       # 작업트리(또는 스테이지)와 최신 커밋의 차이 비교
```

### 3. 파일 상태 흐름
```
untracked(한 번도 커밋 안 함) → unmodified(추적 중, 변경 없음)
      → modified(수정됨, 미반영) → staged(커밋 대기)
```
- 커밋 이력이 있는 파일은 **tracked**, 없는 파일은 **untracked**라고 함. 
- 특정 파일/폴더를 버전 관리에서 제외하려면 `.gitignore` 파일에 이름·확장자를 적어 둔다.

### 4. 되돌리기 명령 정리
| 상황 | 명령 |
|---|---|
| 작업 트리에서 수정한 내용만 취소 | `git restore 파일명` |
| 스테이징만 취소(수정 내용은 유지) | `git restore --staged 파일명` |
| 가장 최근 커밋을 취소(스테이징까지 취소) | `git reset HEAD^` |
| 특정 커밋 시점으로 되돌리고 그 뒤 커밋은 삭제 | `git reset --hard 커밋해시` |
| 커밋은 남기고 특정 커밋의 변경 내용만 취소 | `git revert 커밋해시` |
| 방금 만든 커밋의 메시지 수정 | `git commit --amend` |

- `reset`은 옵션에 따라 `--soft`(스테이징 상태 유지), `--mixed`(기본값, 스테이징 해제), `--hard`(작업트리까지 되돌림)로 나뉨. 
- `restore`/`switch`는 예전에 한 명령(`checkout`)이 담당하던 기능을 나눠 놓은 것.(수정 취소 → `restore`, 브랜치 전환 → `switch`)

### 3장. 깃과 브랜치 (p.79~123)

### 1. 브랜치가 필요한 이유
저장소를 통째로 복사해 여러 버전을 관리하면 파일 중복, 이름 충돌, 나중에 특정 버전만 합치기 어려운 문제가 생긴다. **브랜치** 기능을 이용하면 메인 코드는 그대로 두고 새 기능/수정 작업만 별도 흐름으로 분리했다가, 완성되면 다시 합치는 방식으로 이 문제를 해결할 수 있다. 

- 저장소를 만들면 기본으로 **`main`** 브랜치가 생긴다.
- 브랜치를 새로 만드는 것을 **분기(branch)**, 다시 합치는 것을 **병합(merge)** 이라 한다.

### 2. 브랜치 관련 명령
```bash
git branch                 # 브랜치 목록 확인 (앞에 * 표시된 게 현재 브랜치)
git branch 이름             # 새 브랜치 생성
git switch 이름             # 브랜치 전환(예전 명령: checkout)
git branch -d 이름          # 병합 완료된 브랜치 삭제 (강제 삭제는 -D)
git log --oneline --branches --graph   # 브랜치·커밋 관계를 그래프로 확인
git log main..apple        # main엔 없고 apple에만 있는 커밋 확인
```

- 새 커밋은 **현재 브랜치에만** 반영되고 다른 브랜치에는 영향을 주지 않는다.
- `HEAD`는 지금 작업 중인 브랜치(와 그 최신 커밋)를 가리키는 포인터라고 생각하면 된다.

### 3. 병합(merge) 케이스별 정리
```bash
git switch main
git merge 브랜치명
```
1. **서로 다른 파일**을 각 브랜치에서 만든 경우 → 자동으로 합쳐짐
2. **같은 파일의 다른 부분**을 수정한 경우 → 깃이 자동으로 합쳐줌 (Auto-merging)
3. **같은 파일의 같은 부분**을 수정한 경우 → **충돌(conflict)** 발생 → VS Code의 병합 편집기에서 "현재 수락/수신 수락/두 사항 모두 수락" 중 골라 직접 해결한 뒤 다시 add·commit

- 분기 이후 main에 변화가 없었다면 포인터만 이동하는 **빨리 감기 병합(fast-forward merge)** 이 일어나고, 이 경우 커밋 메시지 창은 뜨지 않는다.
- **cherry-pick**: 브랜치 전체를 합치지 않고, 다른 브랜치의 특정 커밋 하나만 골라서 현재 브랜치에 적용하는 기능. `git cherry-pick 커밋해시`

### 4장. 깃허브 시작하기 (p.124~160)

### 1. 원격 저장소 개념
- **지역 저장소(local repository)**: 내 컴퓨터의 저장소
- **원격 저장소(remote repository)**: 깃허브 등 인터넷상의 저장소
- 지역 → 원격으로 올리는 것: **푸시(push)**
- 원격 → 지역으로 받는 것: **풀(pull)**
- 둘을 계속 같게 맞추는 것: **동기화(synchronize)**

### 2. 깃허브 가입·저장소 만들기/삭제
- github.com에서 가입 후 우측 상단 `+` → `New repository`로 저장소 생성
- 저장소 화면에서 `Settings` → 맨 아래 `Delete this repository`로 삭제 가능 (저장소명을 정확히 입력해야 삭제됨, 복구 불가)
- 원격 저장소 주소 형식: `https://github.com/아이디/저장소명.git`

### 3. 지역 저장소를 원격 저장소에 연결하기
```bash
git remote add origin 원격저장소주소   # 최초 1회만
git remote -v                        # 연결 확인 (fetch/push 둘 다 표시)
```
- 기본 원격 저장소 이름 관례는 `origin` (기본 브랜치명이 `main`인 것과 비슷한 관례)

### 4. 동기화: push / pull
```bash
git push -u origin main   # 최초 푸시 (-u 옵션으로 브랜치 연결, 이후 옵션 생략 가능)
git push                  # 이후에는 이렇게만 입력
git pull origin main      # 원격의 변경 사항을 지역으로 가져오기 (기본 브랜치면 git pull 만 써도 됨)
```
- 최초 푸시 시 깃허브 로그인 인증(브라우저 인증 또는 Git Credential Manager)이 필요하며, 한 번 인증하면 이후엔 다시 묻지 않음. 
- 깃허브 웹 화면에서 직접 파일을 만들고 커밋할 수도 있는데, 이 경우 지역 저장소와 버전 차이가 생기므로 `git pull`로 받아와야 함.

### 5. 깃허브 저장소 화면에서 자주 보는 요소
- 브랜치 선택 드롭다운, 브랜치/태그 개수, 파일 검색, `Add file`(새 파일/업로드), 최신 커밋 메시지, 전체 커밋 수, `About`(저장소 소개) 편집 등

### 6. SSH로 깃허브에 접속하기 (p.154~160)
HTTPS 방식은 접속마다(또는 최초 1회) 계정 인증이 필요한 반면, **SSH 방식**은 컴퓨터 자체를 등록해 두고 키 쌍으로 인증한다.

- **프라이빗 키(개인 키)**: 내 컴퓨터에만 보관, 절대 공유 금지
- **퍼블릭 키(공개 키)**: 깃허브 서버에 등록, 외부에 공개되어도 무방
- 접속 시 두 키가 한 쌍인지 확인해서 인증하는 방식이라 매번 비밀번호를 칠 필요가 없다.

```bash
cd ~
ssh-keygen -t ed25519 -C "이메일주소"   # 키 생성 (경로/이름 물으면 그냥 Enter 3번)
cd .ssh
ls -la                                  # id_ed25519(개인키), id_ed25519.pub(공개키) 확인

eval "$(ssh-agent -s)"                  # SSH 에이전트 실행
ssh-add ~/.ssh/id_ed25519               # 개인 키 등록

clip < ~/.ssh/id_ed25519.pub            # 공개 키 내용을 클립보드로 복사
```
그 다음 깃허브 웹 → 우측 상단 프로필 → **Settings → SSH and GPG keys → New SSH key** 에서 제목을 붙이고 복사한 공개 키를 붙여넣어 등록한다. (이후 SSH 주소로 원격 저장소를 연결하는 실습은 161쪽부터 이어짐)
